# Design

## Context

仓库已实现 FastAPI、React 和 SQLite 应用。本次将当日预约表格改为全天时间轴和精简明细，保留会议室选择联动和创建时段可用性；沿用既有 API、数据库和预约规则。动机与业务范围见 [proposal.md](proposal.md)，行为契约见 [specs](specs/)。

当前环境可用 WSL Python 3.10.12、SQLite 3.37.2 和 Node 24.11.0。OpenSpec CLI 通过现有 Windows Node 运行时解析根目录，应用验证使用 Linux 工具。沿用已确认的 FastAPI + React + Vite + TypeScript + SQLite 技术栈及固定依赖版本。

### 已确认的业务决定

原 DOCX 的其他规则保持不变；以下是用户在本次会话中明确确认的补充与澄清，而非未批准的假设。

| 事项 | 已确认结果 | 规格归属 |
| --- | --- | --- |
| 预约窗口 | 服务端当前时刻 ≤ 开始时间 ≤ 当前时刻 + 7×24 小时，包含两端；只限制开始时间 | reservations |
| 预约人 | 使用当前选择的用户，不代他人预约 | demo-users |
| 取消截止 | 当前时刻严格早于会议开始才能取消 | reservations |
| 超级管理员 | 通过用户选择器模拟身份；只有该角色可启用或停用；不增加登录 | demo-users、meeting-rooms |
| 停用后的原预约 | 保留原状态，已有未来预约继续有效，仍限制预约人时间冲突 | meeting-rooms |
| 状态含义与选择 | 会议室按当前北京时间显示“空闲／使用中”；预约记录显示“已预约／已取消”；卡片、列表标题下拉框和创建表单共享会议室选择 | meeting-rooms、reservations |
| 时间口径 | 北京时间，Asia/Shanghai | reservations |

用户已确认以 FastAPI + React + Vite + TypeScript + SQLite 实现。该决定调整框架、构建与测试安排，四份业务规格仍是行为契约。

不存在待确认且会影响范围、验收或本设计的业务问题。常规输入校验及下述技术取舍不引入新用户功能。

## Goals / Non-Goals

**Goals:**

- 开发时使用 FastAPI 和 Vite 两个进程，演示时由 FastAPI 同时承载构建后的 React 页面和 API，只需启动一个本地服务。
- 在服务端集中执行规则，使页面校验、直接请求和并发请求获得一致结果。
- 以事务保护创建、取消和停用，数据成功提交后才返回成功。
- 让当前时刻、数据路径可由测试注入，可靠覆盖时间边界和重启行为。

**Non-Goals:**

- 不引入分布式部署、实时推送或独立数据库服务。
- 不把模拟用户身份扩展成安全登录系统；管理员操作仍遵守选择器的演示身份模型。
- 不在页面中暴露数据库、事务或其他实现细节。

## Decisions

### 1. FastAPI + React + Vite + TypeScript + SQLite

后端使用 FastAPI 提供 JSON API，以 Pydantic 定义请求和响应结构，由 Uvicorn 运行；Python 内置 sqlite3 访问本地文件数据库，tzdata 提供时区数据。前端使用 React 和 TypeScript 编写单页应用，由 Vite 提供开发服务和静态资源构建。

选择理由：用户已选定前后端技术栈；FastAPI 的结构校验和接口文档便于调试，React 组件可清晰表达用户选择、日期、预约展示与表单之间的状态关系。数据库继续采用本地 SQLite，保留单文件持久化和统一服务端校验。候选方案是后端模板配原生 JavaScript，构建步骤更少，但当前选择更适合明确的前后端组件与接口边界。

| 位置 | 职责 |
| --- | --- |
| backend/app | FastAPI 应用工厂、API 路由、Pydantic 模型、业务服务、SQLite 数据访问与初始化 |
| backend/tests | 固定时钟、临时文件数据库下的业务与接口测试 |
| frontend/src | React 页面组件、状态管理、TypeScript 接口类型和统一请求封装 |
| frontend/dist | Vite 构建产物，由后端在演示模式提供 |
| instance/meeting-room.sqlite3 | 项目根目录下的默认持久化数据库，不属于前端资源 |

应用工厂接受数据库路径与时钟依赖。Pydantic 负责输入结构和基础类型校验，容量、时间窗口、所有者、角色和跨记录冲突仍由业务服务校验，不能以自动参数校验代替业务规则。人数采用严格正整数校验，避免布尔值或其他类型被静默转换。

后端测试使用 pytest、FastAPI TestClient 和 HTTPX；前端提供显式的 TypeScript 类型检查命令及 Vite 构建命令，并执行浏览器交互验收。已有依赖声明与前端锁文件记录可复现版本；[FastAPI 测试文档](https://fastapi.tiangolo.com/tutorial/testing/)说明了 TestClient 与 HTTPX 的使用方式。

### 2. 数据模型与状态

| 实体 | 主要字段 | 约束与说明 |
| --- | --- | --- |
| users | id、name、role | role 为 user 或 super_admin；预置张三、李四、王五及一个超级管理员 |
| rooms | id、name、capacity、equipment、enabled | name 唯一；capacity 为正整数；equipment 为设备列表的 JSON 文本；enabled 为布尔值 |
| reservations | id、room_id、booker_id、subject、attendee_count、start_at、end_at、status | 外键关联；人数为正整数；结束晚于开始；status 仅 booked 或 cancelled |

- 起止时间持久保存为 UTC 整数秒，输入非零秒或小数秒先拒绝，不静默截断。
- booked 显示“已预约”，cancelled 显示“已取消”；不设置自动结束任务，不删除取消记录。
- “空闲／使用中”不持久化：针对当前北京日期的 booked 记录，用 start_at ≤ now < end_at 判断是否正在使用。enabled 是独立维度，停用且空闲仍不可预约，停用中的有效会议仍可显示使用中。
- 会议室和预约人的冲突查询分别使用 room_id/status/start_at/end_at、booker_id/status/start_at/end_at 索引；不依赖唯一索引来判定任意区间重叠。
- 每个连接开启外键约束；基础 CHECK 约束防止无效人数、非法枚举和倒置区间，完整时间及跨记录规则由业务服务检查。

三个初始会议室全部启用；通过管理员启用/停用操作演示状态切换规则。设备与容量严格按 DOCX 初始化。不预置预约，避免固定日期使演示失效。

### 3. 北京时间与服务端时钟

使用带时区的时间值和 Asia/Shanghai 解释业务日期。通过 zoneinfo 和 tzdata 保证 Windows、WSL 等环境不依赖主机默认时区。API 接收带偏移的 ISO 时间并转换到北京时间；无时区、无效格式和非半小时刻度返回字段错误。响应按 +08:00 展示。

服务端在取得写事务后采样一次当前时刻，完整保留当前时间的秒和小数秒；不把“现在”舍入为整点或半点。创建时检查 now ≤ start ≤ now + 7 天，取消时检查 now < start。只要求开始时间处于窗口内，结束时间仍只受同日、20:00 和最长 4 小时限制。

前端使用独立的日期与时间输入值，明确显示“北京时间”；构造带 +08:00 的请求，格式化时显式使用 Asia/Shanghai，避免浏览器默认时区改变用户输入。查询日期没有过去日期或 7 天限制。

时钟依赖在测试中固定，生产取实际服务器时间。机器时间的可信度属于本地运行前提，不提供修改业务时钟的产品入口。

### 4. 模拟身份与权限

用户选择器从预置用户列表获取身份。写请求使用 X-Demo-User-Id 传递当前选择的用户 ID，服务端查表确认身份并按角色与预约所有者判断权限。创建请求不需要 booker_id；若请求带入与当前用户不一致的预约人字段，明确拒绝。

普通用户可以查询、为自己预约和按规则取消自己的预约。超级管理员具有相同预约能力，额外可以停用和恢复启用会议室，仍不能取消他人的预约。启用操作与停用使用同样的角色校验。

选择器在首次加载时默认普通用户张三；是否记住上次选择不作为业务能力，本次不保存该界面偏好。身份来自选择器，不具备真实认证保证；该限制与用户确认的无登录 Demo 范围一致。

### 5. 创建、取消与启用状态变更使用同一事务边界

数据库访问保持同步，涉及 sqlite3 的 API 使用普通 def 路由，由 FastAPI 在线程池中执行；连接在同一次同步业务调用内创建、使用并关闭，不全局共享连接，也不将同步数据库调用直接塞入异步事件循环。[FastAPI 并发文档](https://fastapi.tiangolo.com/async/#path-operation-functions)说明了普通 def 路由的执行方式。使用 FastAPI 不改变下述事务要求。

创建时以 BEGIN IMMEDIATE 开始写事务，再依次读取当前用户、目标会议室及服务端当前时刻，完成字段、时间、人数和 enabled 校验，检查两类重叠后插入 booked 记录，提交后返回成功。区间统一按半开区间处理，重叠条件为 existing.start < requested.end 且 existing.end > requested.start，过滤 status = booked。

取消事务检查当前用户是所有者、原状态为 booked、当前时刻早于开始时间，然后改为 cancelled 并提交。再次取消已取消记录返回明确的“该预约已取消”，不重复改变数据。

启用和停用共用状态变更事务，检查当前用户角色后仅将 enabled 置为目标值，不改变任何预约。重复请求相同状态仍返回成功，不产生额外状态。所有写流程均在失败时回滚；启用失败必须保持原停用状态。

SQLite 的写事务串行化，使两个请求不能同时通过旧数据的冲突检查后写入；停用与创建也按事务先后形成明确结果：先完成停用则创建失败，先完成创建则该预约被保留。对数据库锁等待设置有限超时，超时返回“系统正忙，请稍后重试”，不宣告成功。

停用会议室的 booked 记录不得从预约人冲突查询中过滤。已取消记录则同时退出会议室和预约人的冲突计算。客户端仅用于提示，不能代替这些服务端检查。

候选方案是仅在表单提交前查询冲突，或检查后单独写入；这不能保证同时提交时不重复占用，故使用覆盖检查和写入的单个事务。

### 6. 页面和接口

React 单页依次提供用户选择器、会议室列表、日期查询和预约时间轴及明细、创建表单，分别组织为组件。通过组件状态和 Hooks 管理当前用户、日期、时段、表单及加载/错误状态；用统一的 TypeScript 请求封装访问相对路径 /api，定义会议室、用户、预约和错误响应类型。

查询与创建共用日期和 roomId。卡片提供可键盘操作的选择按钮和选中边框；当日预约标题内嵌会议室下拉框，和创建表单的下拉框均修改同一个 roomId。列表渲染前按 roomId 过滤，但所选日期的完整预约仍保留用于预约人跨会议室冲突判断。停用会议室可以通过卡片和标题下拉框选中查看，创建表单禁止提交。管理员启用/停用按钮与卡片选择目标分开，避免误选。该 Demo 保持单页，不增加多页面路由或全局状态框架。

当日预约改为 ReservationSchedule：上方固定展示横向 08:00～20:00 时间轴，下方用紧凑列表保留全部记录、主题、预约人、人数、时间、状态及本人取消入口。时间轴以所选北京日期的 08:00 为起点，将 booked 记录的开始偏移和时长转换为全天 12 小时的百分比位置与宽度；取消记录只出现在明细中。以 24 格表示半小时刻度，整点标注时间，窄屏减少文字标注密度但保留全部刻度，避免水平滚动。色块有文字可读取的时间与主题信息，明细中的完整时间不依赖颜色或悬浮显示。色块仅展示占用，不新增点击选时或编辑预约交互。

时间轴使用已按会议室过滤的数据，不能直接采用包含本人跨会议室冲突的表单可用时间。只有所选日期数据就绪时才展示占用与空档；加载、读取失败和日期为空分别显示提示，避免把未知显示为空闲。停用房间保留时间轴并说明仅供查询。空白只代表该房间无有效预约，创建是否可选仍受本人冲突、时间窗口与启用状态等原规则约束。沿用既有定时和操作后刷新，无额外接口、依赖或数据模型。

新增纯时间可用性计算：从所选日期记录中保留 booked 且属于目标会议室或当前预约人的区间。每个开始候选必须能安排至少 30 分钟会议；每个结束候选对整个 [start,end) 检查重叠、30～240 分钟、同日营业时间及开始时间窗口。只检查时间点是否被占用会错误允许跨过中间会议，因此必须校验完整区间。端点相接允许。该纯函数用 Node 内置测试执行，不新增测试库。

选项 disabled 状态与灰色样式同步，并提供不可用标识。数据未就绪、读取失败、停用房间和无效区间均禁用提交；不静默改动既有输入。用户主动修改开始时间时，结束时间默认取下一半小时。所选日期数据每 30 秒、页面重新可见及成功操作后更新；收到 room_conflict 后也刷新，保留原时段但标为不可用，要求用户重新选择。

前端单独读取当前北京日期的预约和会议室数据，与所选查询日期的预约分开保存。沿用服务端时钟偏移和每秒 tick，按半开区间计算当前使用状态，到开始/结束时刻自动更新。当前日期变化时重新读取当日数据；成功写操作后立即刷新，每 30 秒及页面重新可见时也刷新，以获取其他用户产生的变化。读取失败显示状态暂不可用，不把未知数据视为空闲。

桌面 workspace 网格使用 stretch 让当日预约和创建预约卡片等高；预约卡片内部使用纵向 flex，让列表填充剩余高度、说明位于底部，不设置截断内容的固定高度。窄屏保持自然堆叠。

| 接口 | 职责 |
| --- | --- |
| GET / | 演示模式返回 React 构建生成的 index.html；开发模式页面由 Vite 提供 |
| GET /api/users | 返回预置用户及角色 |
| GET /api/rooms | 返回会议室基础信息和启用状态 |
| GET /api/reservations?date=YYYY-MM-DD | 返回该北京日期的预约和所需展示字段，包含已取消及停用会议室的记录 |
| POST /api/reservations | 根据当前用户创建预约，字段为 room_id、subject、attendee_count、start_at、end_at |
| POST /api/reservations/{id}/cancel | 当前预约人按时间规则取消 |
| POST /api/rooms/{id}/disable | 当前超级管理员停用会议室 |
| POST /api/rooms/{id}/enable | 当前超级管理员恢复启用会议室 |

接口响应附带服务端当前时刻，供界面提示时间限制并同步当前状态时钟；最终预约校验仍以提交时服务端时间为准。使用既有日期查询接口读取当前北京日期，无需新增使用状态写接口。

创建、取消、启用或停用成功后重新加载所选日期预约及当前概况数据。请求完成前禁用对应提交按钮防止误触，失败时保留用户输入并展示原因。普通用户不显示启用/停用按钮；取消按钮只对本人尚未开始的已预约记录提供，但服务端始终再次校验。

### 7. 可理解的错误与不变性

错误响应统一包含 error.code、error.message 和必要的 details。400 用于字段或当前用户无效，403 用于权限不足，404 用于资源不存在，409 用于业务冲突或操作时状态已不允许，503 用于数据库繁忙，500 用于其他存储失败。页面展示 message，不显示原始异常或仅显示 HTTP 状态码。

为 FastAPI 的 RequestValidationError、HTTP 异常及业务异常注册统一处理器，将默认参数校验响应转换为上述 400 和可理解的中文说明，并在 OpenAPI 中声明实际响应契约；不将默认 detail 数组或框架异常直接作为页面提示。[FastAPI 错误处理文档](https://fastapi.tiangolo.com/tutorial/handling-errors/#override-request-validation-exceptions)提供了覆盖校验异常的机制。

会议室冲突消息只说明会议室及冲突时段已被预约，例如“A101 在 09:00～10:00 已被预约”，不包含原预约人姓名或身份信息。前端请求封装保留 error.code，创建预约收到 room_conflict 时以原生 dialog 的模态弹窗展示，作为同时操作后的服务端容错。弹窗提供确认按钮和 Esc 关闭，保留表单输入；关闭时优先恢复提交按钮焦点，提交已禁用时回到可操作的表单控件。其他错误仍使用页面提示。预约人冲突说明当前用户已有预约及对应会议室、时段；容量、过去时间、超过 7 天、已开始不能取消和停用限制分别给出对应原因。

只有事务提交成功才返回成功；失败响应不触发成功提示或虚构本地记录。读取失败显示“暂时无法读取预约，请稍后重试”等说明，并保留当前页面上下文。

### 8. 持久化与启动

默认数据库为项目根目录下 instance/meeting-room.sqlite3，根据后端模块位置解析项目根目录和绝对路径，避免从 backend、frontend 或其他工作目录启动时误建新数据库；支持 MEETING_ROOM_DB_PATH 指定测试或演示数据文件。数据库不放入 frontend/dist，重新构建前端不能覆盖业务数据。目录与表首次启动时创建。

初始化在事务内使用稳定 ID 和唯一约束补充缺失基础数据；不覆盖已有 rooms.enabled，不清空预约，不把 cancelled 恢复为 booked。重启仅复用原数据库。测试使用独立临时路径，绝不通过生产初始化重置演示数据。

首次实施没有旧数据库迁移需求。后续如改变数据结构，另行规划迁移；不预建本次用不到的迁移平台。

开发模式在本机运行 Uvicorn（约定端口 8000）和 Vite（约定端口 5173）。React 统一请求相对路径 /api，Vite 将 /api 原路径代理至后端，并保留 X-Demo-User-Id 请求头；浏览器无需跨域直连后端，也不额外开放跨域来源。代理配置依据 [Vite server.proxy 文档](https://vite.dev/config/server-options.html#server-proxy)。

演示模式先在 frontend 执行 npm ci、npm run typecheck 和 npm run build，得到 frontend/dist，再只启动 Uvicorn。FastAPI 的根路径返回构建后的 index.html，/assets 挂载构建产物静态目录；API、框架接口文档和静态资源路由分别注册。构建产物的路径按项目根目录解析，不能依赖启动工作目录。不存在的 /api 路径必须返回 API 的 JSON 404，不能回退成 HTML。静态目录服务采用 [FastAPI StaticFiles](https://fastapi.tiangolo.com/tutorial/static-files/)。

尚未构建前端时，后端 API 仍可供开发与测试；演示入口给出先构建前端的明确说明，不影响 API 启动。README 分别记录开发时的两个启动命令，以及前端构建后只启动后端的演示命令。完成构建后，演示运行阶段不需要 Vite 进程。

## Risks / Trade-offs

- [选择器模拟身份无法提供真实安全认证] → 仅用于本机演示，清楚说明身份模型，同时在服务端验证当前选择的用户、角色和所有者。
- [七天窗口随时钟前进，页面打开后选项可能过期] → 在服务端事务内采样时钟并给出具体失败原因；测试用固定时钟验证，不依赖演示当天硬编码时间。
- [SQLite 写锁使同时写入等待] → 写事务仅执行必要校验与写入，设置有限等待和明确繁忙反馈；本机 Demo 不引入多节点部署。
- [状态切换误改预约内容] → 启用与停用均只更新 enabled；测试校验已预约与已取消记录均不变。
- [其他用户写入后当前概况短暂过期] → 每 30 秒和页面重新可见时刷新，本页面成功操作后立即刷新；时间边界每秒更新，提交时仍由服务端检查，不增加实时推送。
- [主机时区或工作目录差异导致时间和数据位置漂移] → 显式时区和偏移、提供 tzdata、按项目根目录解析数据库路径，并在不同默认时区及工作目录下验证。
- [前端构建与开发代理增加启动步骤] → 固定依赖与锁文件，在 README 分别给出开发和演示命令，构建后由后端统一提供静态资源；在选定的同一运行环境中验证端口和工具路径。
- [框架默认错误结构与既定反馈契约不同] → 统一处理 FastAPI 校验异常与 HTTP 异常，用接口测试验证中文消息、状态码和 error 结构。

## Migration Plan

1. 沿用现有 API、enabled 字段及数据库文件，将预约表格替换为时间轴与明细组件，无表结构迁移或数据重置。
2. 更新浏览器验收，检查比例位置、08:00/20:00 边界、首尾相接、取消释放、未知状态及移动端；运行前后端测试、前端类型检查和构建。
3. 刷新构建后的页面验证时间轴、明细、选房联动、时段禁用和并发容错；复用同一数据库文件并验证预约及启停状态保留。
4. 若后续实施需回退版本，保留原数据库文件；本次无旧版本数据迁移或删除动作。

# Proposal

## Why

群聊人工预约难以避免会议室和预约人时间冲突，也难以追踪取消记录。本变更按《轻量级会议室预约系统_Demo需求说明.docx》及用户已确认的业务边界，规划一个可本机演示、数据可持久保存的会议室预约 Demo，并保留 SDD 开发与验证过程。

## What Changes

- 展示 A101、A102、B201 的名称、容量、设备、启用状态及当前北京时间的“空闲／使用中”状态；卡片支持选中，并与当日预约标题中的会议室下拉框和创建表单联动。
- 使用用户选择器模拟当前用户；只有超级管理员能停用或恢复启用会议室，状态切换后展示对应的反向操作。不增加登录或其他会议室管理操作。
- 按日期和所选会议室展示全天时间轴和精简预约明细，标题显示相应会议室名称；时间轴覆盖 08:00～20:00，色块按有效预约时长占位、留白表示空档，已取消记录仅保留在明细中。明细列出主题、预约人、人数、起止时间和“已预约／已取消”状态，并保留取消操作及历史、停用会议室记录。
- 创建预约时校验营业时间、30 分钟刻度、30 分钟至 4 小时时长、人数容量、会议室冲突、预约人跨会议室冲突，并立即更新当前界面。
- 按用户确认，预约人固定为当前用户；预约开始时间必须在服务端当前时刻至 7 天后同一时刻之间，包含两端；统一使用北京时间。
- 预约人只能在会议开始前取消自己的预约；取消保留记录并释放时段。停用会议室的已有未来预约继续有效。
- 持久保存会议室、用户和预约数据；为校验失败、权限不足、冲突及保存失败提供可理解的反馈。
- 交付可在本机运行的源码、README、SDD 文档、主要 AI 会话记录和验证记录。展示方式采用全天时间轴、精简明细和创建表单，技术方案详见设计。
- 当日预约和创建预约卡片在并排布局中保持等高；会议室当前状态独立于日期查询和创建表单的时段，并随时间及预约数据变化更新。
- 会议室时间冲突以弹窗反馈，仅说明会议室和时段已被预约，不显示原预约人姓名；关闭弹窗后保留表单输入。
- 创建表单依据有效预约和既有业务规则禁用不可用时间选项，包括被占用时段和跨越占用区间的结束时间；服务端冲突校验及弹窗继续处理同时提交的情况。

本次不包含预约修改、审批、通知、重复会议、参会人员名单、用户管理、公网部署或复杂视觉设计。所有业务歧义已通过本次会话确认；技术实现选择不扩展上述业务范围。

## Capabilities

### New Capabilities

- `meeting-rooms`: 会议室概况、当前使用状态，以及超级管理员启用/停用操作和对既有预约的影响。
- `demo-users`: 用户选择器、当前预约人来源，以及普通用户和超级管理员的模拟权限边界。
- `reservations`: 按日期查询、创建预约的全部规则、本人取消、状态显示和业务失败反馈。
- `data-persistence`: 基础数据初始化、会议室及预约生命周期的持久保存，以及刷新与重启后的数据一致性。

### Modified Capabilities

无。当前项目没有既有业务代码或主规格。

## Impact

- 项目已实现预约应用；本次按用户确认将当日预约表格改为全天时间轴和精简明细。沿用现有 API 与业务规则，无数据库结构迁移。
- 按用户确认采用 FastAPI + React + Vite + TypeScript + SQLite：FastAPI 提供业务 API，React 提供交互界面，SQLite 保存本地数据；本次在既有应用结构、依赖声明和测试上增量修改。
- 开发时分别运行 FastAPI 与 Vite，前端通过开发代理访问 API；本机演示时先构建前端，再由 FastAPI 提供页面与静态资源，仅运行一个后端服务。
- 新增会议室、用户、预约及停用操作的应用接口；所有业务校验在服务端执行，客户端提供对应交互提示。
- 后端使用 pytest 与 FastAPI TestClient 验证时间边界、容量、两类冲突、取消权限、管理员停用、并发提交和重启持久性；前端执行 TypeScript 类型检查、Vite 构建和浏览器交互验证，并提供开发及单服务演示的可复现步骤。
- 同步更新 OpenSpec 规格、设计和增量任务，并在 apply 阶段验证启用权限、持久性、当前时间边界和卡片布局。
